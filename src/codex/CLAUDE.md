# src/codex/ — Cardex, Skilldex, and Eventmaps

This directory hosts three tools: **Cardex** (`cards.tsx`), **Skilldex** (`skills.tsx`), and **Eventmaps** (`events.tsx`), sharing `components/`, `hooks/`, `utils/`, and `types/`.

## Key files
- `components/SearchPanels/` + `components/ResultsPanels/` — per-tool search UI and result rendering (incl. `TalentTree`, `EventTree`)
- `components/shared/ZoomSlider/` — the zoom control for both trees, `orientation: 'horizontal' | 'vertical'`. Horizontal sits in the Eventmaps search panel; `StickyZoomSlider/` wraps a vertical one in the floaty fixed container used by Eventmaps *and* Skilldex (its `position` prop picks the screen edge). Same DOM in both orientations — the layout differences are CSS-only.
- `hooks/useSearchFilters/` — filter state + filtering logic (`talentTreeFilter.ts` is concrete/talent-specific by design; don't re-generalize for one consumer). `useCardSetFilters.ts` exports **two** hooks — see the nil-expansion invariant below
- `utils/tree/` — infrastructure **shared by talent and event trees**: text-width estimation, node-dimension factory, tree helpers, SVG setup. Fix bugs here once, not per-feature.
- `utils/eventTreeSpacing/` — event-tree layout: `d3-flextree` (variable-width tidy layout) + a multi-parent centering pass for refChildren, plus the vertical spacing pass; read its `README.md` before touching it
- `data/event-trees.json` — static event data, regenerated by `scripts/sync-events.js` (never hand-edit)

## Invariants
- **Layout/render split**: tree layout is memoized on tree/filter/formatting inputs; zoom only re-renders. Both tree components are `React.memo`'d and take scalar props, not whole hook-result objects. Don't merge the layout and render effects back together, and don't add `zoomLevel` to either layout memo's deps — that's what keeps zooming off the dimension-caching path.
- **Zoom commits on drag end, not continuously**: `ZoomSlider` tracks a local pending index while dragging and only calls `setZoomLevel` from `onChangeEnd`. A full redraw per slider step would be wasteful, and dragging *through* the Cover stop would make `useEventTreeZoom` re-measure and re-cache its `coverScale` from mid-drag container dimensions.
- Zoom values come from `ZOOM_STOPS` in `constants/zoomValues.ts` (`ZoomLevel = 'cover' | number`). Adding or removing a stop is a one-line array edit; the numbers are not literal percentages for large event trees (they interpolate cover→actual) or for talent trees (a depth multiplier applies).
- Node-dimension caches are keyed by all rendering settings; the event cache is cleared only on event change/unmount, not per settings change.
- **Nil (0) expansion is labelled `Core°` in Cardex, shows no card set at all in Skilldex, and is only *selectable* in Cardex.** `useCardSetFilters.ts` exports `useCardSetFilters` (Cardex) and `useTalentCardSetFilters` (Skilldex) over a shared base: the base remaps index 0 → Core for the *name*, but only Cardex remaps it for *selection*. Talents use expansion 0 as a structural marker (event-only talents, offers, some unavailable talents) and are filtered by their own tree sections, so they must stay visible when Core is unticked — `isIndexSelected(0)` must stay false there. Never put index 0 in the shared `indexMap`/`indexToValueMap`: that would make it selectable for talents too. Cardex renders the Core name plus a `°` span; Skilldex excludes index 0 in **both** `TalentTree`'s `shouldShowCardSet` (dimensions) and its `getCardSetName` (render) — those two must agree, or nil nodes reserve height for a row they never draw.
- **Every filter mutator must be listed in `TRACKED_FILTER_HANDLERS`.** `useFilterTracking`'s `hasUserChangedFilter` is a one-way latch meaning "the user has interacted at all" — it gates the debounced cache write so that mounting with cached filters doesn't immediately re-save them. `createTrackedFilter(hook, names)` wraps only the named functions, so a mutator left off the list applies visibly but never reaches localStorage and reverts on reload. The lists cover toggles *and* the bulk `enable*`/`reset*`/undo functions; add to them when a filter hook gains a new mutator. Nothing type-checks this — the failure mode is a filter change that silently doesn't persist.
- **Adding or removing a filter option does not need a `codexFilterStore.ts` version bump.** `createFilterHook` merges the cached blob by iterating the *cache* but gating on `key in defaultFilters`, so stale keys are dropped and missing keys fall back to the default. Removing an option silently ignores the cached value; the key is purged from localStorage on the next debounced write. Only bump the version if the *meaning* or value type of an existing key changes.
- **Monster cards are rarity 4 / banner 11 — *not* card type 7.** Cardex treats monster cards as one opt-in population behind the single *Include Monster cards* checkbox in Extras, so every filter group whose `indexMap` can address them must defer to `shouldIncludeMonsterCards` for them (see `isCardMatching` in `useAllCardSearchFilters.ts`). Rarity and banner get this for free — indices 4 and 11 are absent from their `indexMap`s, so nothing can select them. **Card type is the dangerous case**: ~1000 monster cards carry an ordinary type (mostly Utility), all of which *are* selectable, so keying the deferral on the card's type instead of on the card lets the Type group silently veto monster cards the user opted into. Type 7 invites exactly that mistake — it looks like a monster marker but sits on only ~10 cards, one of which (`Infernal Racket`) `getActualColor` deliberately remaps to a normal banner. It has no checkbox, and stays in `indexToValueMap` only so those cards render a label. Verify changes here against the live `cards-codex` payload rather than by eye: the failure mode is one filter combination over ~1000 cards.
- **`.result-card__name`'s widths are minimums, not fixed sizes.** Its `flex-shrink: 1` + `min-width: 0` are what let the `CardMetadata` pill stay pinned to the right edge of the title row on narrow widths — the pill is `flex-shrink: 0`, so the name is the only element that can give. Restoring hard widths there pushes the pill off the edge or overflows the row on mobile.
- Cards/talents come from Supabase (24h localStorage cache; versioned keys in `codexCardsStore.ts` / `codexTalentsStore.ts`); events come from the static JSON. `getActualExpansion`/`getActualColor` in `cardsResponseMapper.ts` run at **map time, not render time** — after changing them, force a **Resync data** (or clear `codex_cards_v2`) or you are looking at cards mapped by the old code.
- **Card and talent artwork is resolved through the module-scope `Map` in `@/shared/hooks/useCardImageSrc`**, never a per-render linear `.find` over the ~3100-entry `card-artwork.json` — Cardex resolves artwork once per rendered row. Cardex uses the hook; Skilldex uses the plain `getCardImageSrc` from the same module, because its nodes are drawn by D3 outside React's render. Talents resolve against the *same* card mapping (Blightbane treats talents as cards, art in the same `/images/icons/` namespace), so don't add a talent-specific mapping or an artwork field to the Talents table. Lookups must use the JSON's key verbatim: some artwork names carry curly apostrophes, typos, and set suffixes (`"Typhon's Cunning"` → `"Thyphon’s cunning_eclypse-miniset"`), so no amount of transforming a card name produces the filename, and normalizing quotes on either side of the lookup breaks it. A missing name or `artwork: null` is the **only** reliable miss signal: blightbane.io serves a valid placeholder webp with HTTP 200 for non-existent icons, so `onError` never fires for a wrong artwork value.
- **`requirements` render on `choice`, `result`, `dialogue` *and* `end` nodes** — `isRequirementsNode` in `eventNodeDimensions.ts` gates both the width calculation and the box height, and `renderTextNodeContent` draws the box for the text-node types. Dialogue/end nodes carry requirements when a `[?condition]` conditional in the Ink gates that line (see the conditional-variant section of `scripts/parse/README.md`), and the parser's engine-test shape depends on them being visible: narrowing the guard back to choice/result would silently hide 21 nodes' conditions rather than fail. The dimension helper and the renderer must agree on the box's place in the vertical stack (text → effects → requirements → continues → loop), or nodes reserve height for a box drawn elsewhere.
- Tree layout/rendering changes are verified **visually** (before/after comparison in the dev server, incl. expanded/collapsed nodes and zoom levels), not with unit tests. The **user** runs the dev server and does the comparison — don't start one yourself; say what changed and which states to look at (see Working Style in the root `CLAUDE.md`).
