# src/codex/ — Cardex, Skilldex, and Eventmaps

This directory hosts three tools: **Cardex** (`cards.tsx`), **Skilldex** (`skills.tsx`), and **Eventmaps** (`events.tsx`), sharing `components/`, `hooks/`, `utils/`, and `types/`.

## Key files
- `components/SearchPanels/` + `components/ResultsPanels/` — per-tool search UI and result rendering (incl. `TalentTree`, `EventTree`)
- `components/shared/ZoomSlider/` — the zoom control for both trees, `orientation: 'horizontal' | 'vertical'`. Horizontal sits in the Eventmaps search panel; `StickyZoomSlider/` wraps a vertical one in the floaty fixed container used by Eventmaps *and* Skilldex (its `position` prop picks the screen edge). Same DOM in both orientations — the layout differences are CSS-only.
- `hooks/useSearchFilters/` — filter state + filtering logic (`talentTreeFilter.ts` is concrete/talent-specific by design; don't re-generalize for one consumer). `useCardSetFilters.ts` exports **two** hooks — see the nil-expansion invariant below
- `utils/tree/` — infrastructure **shared by talent and event trees**: text-width estimation, node-dimension factory, tree helpers, SVG setup. Fix bugs here once, not per-feature.
- `utils/eventTreeSpacing/` — event-tree layout: `d3-flextree` (variable-width tidy layout) + a multi-parent centering pass for refChildren, plus the vertical spacing pass; read its `README.md` before touching it
- `data/event-trees.json` — static event data, regenerated by `scripts/sync-events.js` (never hand-edit). Its source is `scripts/data/events.json` from an external event-extraction tool; `npm run sync-events -- --from-dump` regenerates from a Blightbane bundle scrape instead

## Invariants
- **Layout/render split**: tree layout is memoized on tree/filter/formatting inputs; zoom only re-renders. Both tree components are `React.memo`'d and take scalar props, not whole hook-result objects. Don't merge the layout and render effects back together, and don't add `zoomLevel` to either layout memo's deps — that's what keeps zooming off the dimension-caching path.
- **Zoom commits on drag end, not continuously**: `ZoomSlider` tracks a local pending index while dragging and only calls `setZoomLevel` from `onChangeEnd`. A full redraw per slider step would be wasteful, and dragging *through* the Cover stop would make `useEventTreeZoom` re-measure and re-cache its `coverScale` from mid-drag container dimensions.
- Zoom values come from `ZOOM_STOPS` in `constants/zoomValues.ts` (`ZoomLevel = 'cover' | number`). Adding or removing a stop is a one-line array edit; the numbers are not literal percentages for large event trees (they interpolate cover→actual) or for talent trees (a depth multiplier applies).
- Node-dimension caches are keyed by all rendering settings; the event cache is cleared only on event change/unmount, not per settings change.
- **Nil (0) expansion is labelled `Core°` in Cardex, shows no card set at all in Skilldex, and is only *selectable* in Cardex.** `useCardSetFilters.ts` exports `useCardSetFilters` (Cardex) and `useTalentCardSetFilters` (Skilldex) over a shared base: the base remaps index 0 → Core for the *name*, but only Cardex remaps it for *selection*. Talents use expansion 0 as a structural marker (event-only talents, offers, some unavailable talents) and are filtered by their own tree sections, so they must stay visible when Core is unticked — `isIndexSelected(0)` must stay false there. Never put index 0 in the shared `indexMap`/`indexToValueMap`: that would make it selectable for talents too. Cardex renders the Core name plus a `°` span; Skilldex excludes index 0 in **both** `TalentTree`'s `shouldShowCardSet` (dimensions) and its `getCardSetName` (render) — those two must agree, or nil nodes reserve height for a row they never draw.
- **Talent artwork is flush with the node's left edge, fills the name row's height, and is `WIDTH_SCALE` times as wide** — the square 70×70 source is scaled to cover that wider window with `slice`, so only its middle horizontal band shows. Widening trades vertical crop for horizontal coverage, *not* resolution: at `WIDTH_SCALE: 1.5` the scale is ~1.0× and ~67% of the source's height is visible. **Artwork does change node height**, via `NODE.ARTWORK.EXTRA_ROW_HEIGHT` added to the name row — which is why `getNameRowHeight` in `talentNodeDimensions.ts` is shared by the dimension engine *and* the renderer rather than duplicated. Changing that dial is safe precisely because both paths read the one function; writing the sum out twice is what the nil-card-set invariant warns against.
- **The name's layout ignores `WIDTH_SCALE` on purpose.** It's centred in the space beside a *square* artwork, so widening never moves the text — the wider art passes underneath and a `<linearGradient>` mask (`FADE_WIDTH`) fades it out before it reaches the glyphs. Recentring the name against the widened art instead would squeeze long names and push them off-centre. The placeholder square is deliberately **not** masked: a faded flat rect reads as a rendering glitch where a crisp one reads as "no art".
- **The flush-left artwork clips to `NODE.CORNER_RADIUS`, which must match `.talent-node`'s `rx`/`ry`.** Flush on two edges means the square art overlaps the node's rounded corners, so it's clipped to a hand-built path (`roundedLeftEdgePath`) rather than `rx`/`ry` — only the *left* corners round, and only when the name row is the node's first/last row. The bottom-left case is live: with description, Blightbane link and additional requirements all absent, the name row **is** the whole node. Corner flags are computed in `renderTalentNode`, which is the only place that knows what sits below the name row. Nothing type-checks the radius against the stylesheet; both sides carry a comment.
- **Positioning anything beside `.talent-node-name` requires *measuring* the name.** It's SVG `text` with `text-anchor: middle`, so D3 reports no width and a guessed offset silently overlaps the glyphs (exactly how the first artwork attempt broke). `talentTextMeasurer.ts` has variants matching the name's three font states (`name` / `nameCollapsed` / `nameCollapsedLong`) — **those must stay in sync with `.talent-node-name`'s font sizes and weight in the stylesheet**. The name is centred in the space *remaining* beside the icon, not on the node, and truncated with `truncateTalentName` (SVG `text` has no `text-overflow: ellipsis`) at `NODE.ARTWORK.NAME_MAX_WIDTH_RATIO` of that space.
- **Talent artwork has no higher-resolution source than 70×70.** Probed `images/cards/`, `images/large/`, `images/full/`, `images/icons_large/`, `images/cards_full/` and `.png`: all return the same 3826-byte placeholder with HTTP 200 (a deliberately bogus filename does too), and the `.png` is the same 70×70 at 4× the bytes. A full-width 200px strip was tried first and looked visibly pixelated at that 2.9× upscale — so the name row's height doubles as the crispness ceiling, and displaying talent art much larger anywhere will look soft no matter how it's fetched. A talent missing from the mapping draws the flat placeholder square, so the name's position never depends on whether the mapping resolved.
- **Every filter mutator must be listed in `TRACKED_FILTER_HANDLERS`.** `useFilterTracking`'s `hasUserChangedFilter` is a one-way latch meaning "the user has interacted at all" — it gates the debounced cache write so that mounting with cached filters doesn't immediately re-save them. `createTrackedFilter(hook, names)` wraps only the named functions, so a mutator left off the list applies visibly but never reaches localStorage and reverts on reload. The lists cover toggles *and* the bulk `enable*`/`reset*`/undo functions; add to them when a filter hook gains a new mutator. Nothing type-checks this — the failure mode is a filter change that silently doesn't persist.
- **Adding or removing a filter option does not need a `codexFilterStore.ts` version bump.** `createFilterHook` merges the cached blob by iterating the *cache* but gating on `key in defaultFilters`, so stale keys are dropped and missing keys fall back to the default. Removing an option silently ignores the cached value; the key is purged from localStorage on the next debounced write. Only bump the version if the *meaning* or value type of an existing key changes.
- **Monster cards are rarity 4 / banner 11 — *not* card type 7.** Cardex treats monster cards as one opt-in population behind the single *Include Monster cards* checkbox in Extras, so every filter group whose `indexMap` can address them must defer to `shouldIncludeMonsterCards` for them (see `isCardMatching` in `useAllCardSearchFilters.ts`). Rarity and banner get this for free — indices 4 and 11 are absent from their `indexMap`s, so nothing can select them. **Card type is the dangerous case**: ~1000 monster cards carry an ordinary type (mostly Utility), all of which *are* selectable, so keying the deferral on the card's type instead of on the card lets the Type group silently veto monster cards the user opted into. Type 7 invites exactly that mistake — it looks like a monster marker but sits on only ~10 cards, one of which (`Infernal Racket`) `getActualColor` deliberately remaps to a normal banner. It has no checkbox, and stays in `indexToValueMap` only so those cards render a label. Verify changes here against the live `cards-codex` payload rather than by eye: the failure mode is one filter combination over ~1000 cards.
- **`.result-card__name`'s widths are minimums, not fixed sizes.** Its `flex-shrink: 1` + `min-width: 0` are what let the `CardMetadata` pill stay pinned to the right edge of the title row on narrow widths — the pill is `flex-shrink: 0`, so the name is the only element that can give. Restoring hard widths there pushes the pill off the edge or overflows the row on mobile.
- **`blightbane_id` is the game's own internal card/talent id, despite the name.** Blightbane's `id`
  field is not a surrogate key it assigns — it is the id the game uses, which is why static
  game-derived data can be joined on it. Verified against the live `cards-codex` payload: all 2716
  ids in `scripts/data/card-id-mapping.json` that appear there resolve to the same name, zero
  disagreements (the other 386 are talents, absent from the cards endpoint; `specs-card-metadata.md`
  records that all 385 Supabase `Talents.blightbane_id` values match Blightbane's `category=10` ids).
  `data/treasure-cards.json` joins to `CardData` on it in `utils/treasureHelper.ts`. Note the field
  is `blightbane_id` on `CardData` but plain `id` on the raw `CardApiResponse` — `cardsResponseMapper`
  renames it, so don't join a raw API response on `blightbane_id`.
- **Cards and talents come from *different* sources.** Cards are fetched live from the Blightbane `cards-codex` API (`services/cardsApiBlightbane.ts`); only talents come from Supabase (`services/talentsApiSupabase.ts`). Both get a 24h localStorage cache with versioned keys in `codexCardsStore.ts` / `codexTalentsStore.ts`; events come from the static JSON. `services/cardsApiSupabase.ts` is **dead code** — a leftover from when Cardex read the Supabase `Cards` table, kept but imported by nothing; the `Cards` table and its `sync-cards` edge function are dormant for the same reason. Don't reach for Supabase when changing anything about card data. `getActualExpansion`/`getActualColor` in `cardsResponseMapper.ts` run at **map time, not render time** — after changing them, force a **Resync data** (or clear `codex_cards_v2`) or you are looking at cards mapped by the old code.
- **Card and talent artwork is resolved through the module-scope `Map`s in `@/shared/hooks/useCardImageSrc`**, never a per-render linear `.find` over the ~3100-entry `card-artwork.json` — Cardex resolves artwork once per rendered row. Cardex uses the hook; Skilldex uses the plain `getCardImageSrc` from the same module, because its nodes are drawn by D3 outside React's render. Both come from `card-artwork.json` (Blightbane treats talents as cards, art in the same `/images/icons/` namespace), so don't add a talent-specific data file or an artwork field to the Talents table.
- **The same name can carry different artwork per `category`, so pass the category when resolving.** 34 names have multiple entries, 33 with two or more non-null artworks — e.g. `"Bulwark"` is `abilityart_1_59` as a card but `cardart_5_23` as a talent. `getCardImageSrc(name, fallback?, category?)` looks up `name|category` first, then falls back to name-only, then to the fallback image. Cardex passes `card.category`; Skilldex passes the exported `TALENT_ARTWORK_CATEGORY` (**10** — 386 entries, matching the ~385 known talents). The name-only fallback is load-bearing: 19 of those 33 names have no category-10 entry, so a category-only lookup would leave those talents blank. Null artworks are filtered out before either map is built, so they can never shadow a populated sibling. Verified when introduced: all 386 category-10 entries resolve to their own artwork, and 3 cards were *fixed* (`Blessed`, `Runic Repel`, `Siphon Sanity`) with no regressions.
- **A dozen card names still collide on name *and* category with different artwork** (low/high-tide and normal/`_infernal` variants — distinct cards sharing a name), so first-entry-wins picks one arbitrarily. Nothing in `card-artwork.json` separates them; fixing it needs a new discriminator from the Blightbane source data via `scripts/fetch-card-artwork-mapping.js`, not a smarter lookup. Don't add retry or heuristic matching in the hook. Lookups must use the JSON's key verbatim: some artwork names carry curly apostrophes, typos, and set suffixes (`"Typhon's Cunning"` → `"Thyphon’s cunning_eclypse-miniset"`), so no amount of transforming a card name produces the filename, and normalizing quotes on either side of the lookup breaks it. A missing name or `artwork: null` is the **only** reliable miss signal: blightbane.io serves a valid placeholder webp with HTTP 200 for non-existent icons, so `onError` never fires for a wrong artwork value.
- **`requirements` render on `choice`, `result`, `dialogue` *and* `end` nodes** — `isRequirementsNode` in `eventNodeDimensions.ts` gates both the width calculation and the box height, and `renderTextNodeContent` draws the box for the text-node types. Dialogue/end nodes carry requirements when a `[?condition]` conditional in the Ink gates that line (see the conditional-variant section of `scripts/parse/README.md`), and the parser's engine-test shape depends on them being visible: narrowing the guard back to choice/result would silently hide 21 nodes' conditions rather than fail. The dimension helper and the renderer must agree on the box's place in the vertical stack (text → effects → requirements → continues → loop), or nodes reserve height for a box drawn elsewhere.
- Tree layout/rendering changes are verified **visually** (before/after comparison in the dev server, incl. expanded/collapsed nodes and zoom levels), not with unit tests. The **user** runs the dev server and does the comparison — don't start one yourself; say what changed and which states to look at (see Working Style in the root `CLAUDE.md`).
