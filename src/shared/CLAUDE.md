# src/shared/ — infrastructure used by more than one tool

Site-wide building blocks (layout, buttons, modals, icons, registry) are described in the root `CLAUDE.md`. This file covers what Cardex, Skilldex, Eventmaps and Booty share: the card data layer, event data, the search-filter framework and search UI, tree infrastructure and zoom. The tools themselves live in their own folders — including the two tree components (`TalentTree` in `src/skilldex/`, `EventTree` in `src/eventmaps/`) that the tree invariants below constrain.

## Key files

- `components/ZoomSlider/` — the zoom control for both trees, `orientation: 'horizontal' | 'vertical'`. Horizontal sits in the Eventmaps search panel; `StickyZoomSlider/` wraps a vertical one in the floaty fixed container used by Eventmaps _and_ Skilldex (its `position` prop picks the screen edge). Same DOM in both orientations — the layout differences are CSS-only.
- `utils/tree/` — infrastructure **shared by talent and event trees**: text-width estimation, node-dimension factory, tree helpers, SVG setup. Fix bugs here once, not per-feature.
- `data/event-trees.json` — static event data, regenerated by `scripts/sync/sync-events.js` (never hand-edit). Its source is `scripts/data/events.json` from an external event-extraction tool; `npm run sync-events -- --from-dump` regenerates from a Blightbane bundle scrape instead
- `hooks/useSearchFilters/` — the filter framework (`useFilterFactory`, `useFilterTracking`, `useKeywords`) plus `useCardSetFilters`, the one filter group both Cardex and Skilldex use. Each tool's own filter hooks stay in its tool folder.
- `hooks/useCardData.ts` → `services/cardsApiBlightbane.ts` → `utils/cardsResponseMapper.ts`, cached by `utils/codexCardsStore.ts` — the card data layer for Cardex and Booty.

## Invariants

- **Layout/render split**: tree layout is memoized on tree/filter/formatting inputs; **zoom neither re-lays-out nor redraws**. Both tree components are `React.memo`'d and take scalar props, not whole hook-result objects. Each tree has _three_ stages, and they must stay separate: the layout memo, a **draw effect** that builds the SVG (no `zoomLevel` in its deps), and a **zoom effect** that only sets the svg's dimensions and the content group's `scale()`/`translate()` transform via `applyTreeZoom`. Don't merge them back together, and don't add `zoomLevel` to either layout memo _or_ draw effect — redrawing every node to change three attributes cost ~293ms of scripting on Skilldex (`src/specs/inp.md` Part 2). The draw effect calls `setupTreeSvg` with `zoomScale: undefined` and zero offsets because the zoom effect, declared after it, immediately applies the real values — **effect declaration order is load-bearing**. For the same reason the zoom effect's deps must be a **superset** of the draw effect's: a redraw recreates the content group at scale 1 and resets the wrapper's scroll, so a dep present only on the draw effect leaves the tree unzoomed and (on Eventmaps) scrolled hard left until something else triggers the zoom effect. That was a real bug when `showAlteredBadges` was on the draw effect alone. This holds only while no node-drawing code reads the zoom level; `applyTreeZoom` finds the content group by `TREE_CONTENT_GROUP_CLASS`, so that class must stay on it.
- **Zoom commits on drag end, not continuously**: `ZoomSlider` tracks a local pending index while dragging and only calls `setZoomLevel` from `onChangeEnd`. A full redraw per slider step would be wasteful, and dragging _through_ the Cover stop would make `useEventTreeZoom` re-measure and re-cache its `coverScale` from mid-drag container dimensions.
- Zoom values come from `ZOOM_STOPS` in `constants/zoomValues.ts` (`ZoomLevel = 'cover' | number`). Adding or removing a stop is a one-line array edit; the numbers are not literal percentages for large event trees (they interpolate cover→actual) or for talent trees (a depth multiplier applies).
- Node-dimension caches are keyed by all rendering settings; the event cache is cleared only on event change/unmount, not per settings change.
- **Nil (0) expansion is labelled `Core°` in Cardex, shows no card set at all in Skilldex, and is only _selectable_ in Cardex.** `useCardSetFilters.ts` exports `useCardSetFilters` (Cardex) and `useTalentCardSetFilters` (Skilldex) over a shared base: the base remaps index 0 → Core for the _name_, but only Cardex remaps it for _selection_. Talents use expansion 0 as a structural marker (event-only talents, offers, some unavailable talents) and are filtered by their own tree sections, so they must stay visible when Core is unticked — `isIndexSelected(0)` must stay false there. Never put index 0 in the shared `indexMap`/`indexToValueMap`: that would make it selectable for talents too. Cardex renders the Core name plus a `°` span; Skilldex excludes index 0 in **both** `TalentTree`'s `shouldShowCardSet` (dimensions) and its `getCardSetName` (render) — those two must agree, or nil nodes reserve height for a row they never draw.
- **Every filter mutator must be listed in `TRACKED_FILTER_HANDLERS`.** `useFilterTracking`'s `hasUserChangedFilter` is a one-way latch meaning "the user has interacted at all" — it gates the debounced cache write so that mounting with cached filters doesn't immediately re-save them. `createTrackedFilter(hook, names)` wraps only the named functions, so a mutator left off the list applies visibly but never reaches localStorage and reverts on reload. The lists cover toggles _and_ the bulk `enable*`/`reset*`/undo functions; add to them when a filter hook gains a new mutator. Nothing type-checks this — the failure mode is a filter change that silently doesn't persist.
- **Cardex/Skilldex filter URL codes are permanent.** `useCodexUrlParams` writes each checkbox group as `?<param>=<codes>` via the `*UrlCodec` exported next to each filter hook's `indexMap` (absent = all, `none` = empty, `all` accepted on read but never written). Card sets, banners, rarities, card types and tiers use the **game's own ids**, so a new option simply takes the next id; requirements use **named codes** (`dex`, `evt`, …) because their `indexMap` positions are ours and would shift on insertion. Numeric groups compress runs of 3+ options to `a-b`, and a range covers every option with an id inside it — so **the game filling an id gap** (banner 7, card types 5/7) would make old range links include the new option. Never reuse a code for a different option — old shared links would silently select something else; to rename one, keep the old code as an extra read-only entry. Filters applied from the URL go through `enable*`, so those must be in `TRACKED_FILTER_HANDLERS` (below). `?weekly` is honoured only when no other codex param is present.
- **Adding or removing a filter option does not need a filter-store (`cardFilterStore.ts` / `talentFilterStore.ts` / `eventFilterStore.ts`, each in its tool's `utils/`) version bump.** `createFilterHook` merges the cached blob by iterating the _cache_ but gating on `key in defaultFilters`, so stale keys are dropped and missing keys fall back to the default. Removing an option silently ignores the cached value; the key is purged from localStorage on the next debounced write. Only bump the version if the _meaning_ or value type of an existing key changes.
- **A `<rarity:X>` keyword token matches a card's rarity, not its text** (`utils/keywordMatching.ts`, shared by the Cardex filter and `ResultCard`'s pills). It exists because the game scores a capitalized rarity (`Monster`) among a challenge's **base** `scoringParams.keywords` as "every card of that rarity", while a plain `Monster` in the search field is a case-insensitive text search that would list cards merely mentioning it. So the weekly optimization converts only an exact-case rarity in `filterData.keywords` into a token, and turns on _Include Monster cards_ for `<rarity:Monster>`, which otherwise matches nothing. Two things are deliberate: the match against `RARITY_KEYWORDS` is **case-sensitive** (lowercase `monster` is a text keyword in the game too), and a rarity in **`miscPointsRules`** (`specialKeywords`) stays a plain text keyword, since those rules match card text. A hand-typed `Monster` must keep searching text — never infer a rarity from capitalization in the field itself.
- **`blightbane_id` is the game's own internal card/talent id, despite the name.** Blightbane's `id`
  field is not a surrogate key it assigns — it is the id the game uses, which is why static
  game-derived data can be joined on it. Verified against the live `cards-codex` payload: all 2716
  ids in `scripts/data/card-id-mapping.json` that appear there resolve to the same name, zero
  disagreements (the other 386 are talents, absent from the cards endpoint; `src/specs/card-metadata.md`
  records that all 385 Supabase `Talents.blightbane_id` values match Blightbane's `category=10` ids).
  `src/booty/data/treasure-cards.json` joins to `CardData` on it in `src/booty/utils/treasureHelper.ts`. Note the field
  is `blightbane_id` on `CardData` but plain `id` on the raw `CardApiResponse` — `cardsResponseMapper`
  renames it, so don't join a raw API response on `blightbane_id`.
- **Different cards can share a name, so a card's name is not its identity.** 16 names cover 32 distinct cards (low/high-tide pairs, two monsters' `Consume`, …). `sortAndRemoveDuplicates` in `cardsResponseMapper.ts` drops only cards identical in every displayed field (`Divinity`, `Marked`), and marks the rest with `hasDuplicateName`. That flag switches the two name-keyed things over: the Blightbane link (`getBlightbaneCardUrl` → `BlightbaneCardByIdUrl`, since blightbane.io resolves a name to one fixed twin) and the tracked-card key (`getCardStrikeKey` → `name#id`). Every other card keeps its bare name in the saved `struckCards`, so existing progress is untouched; a bare twin name saved before this still ticks both twins until one is unticked (`isCardStruckIn`). React keys use `blightbane_id`. Anything new that keys on `card.name` — a lookup map, a URL, a saved list — has to handle twins the same way.
- **Cards and talents come from _different_ sources.** Cards are fetched live from the Blightbane `cards-codex` API (`services/cardsApiBlightbane.ts`); only talents come from Supabase (`src/skilldex/services/talentsApiSupabase.ts`). Both get a 24h localStorage cache with versioned keys in `utils/codexCardsStore.ts` / `src/skilldex/utils/codexTalentsStore.ts`; events come from the static JSON. Cardex once read the Supabase `Cards` table; its fetcher has been deleted, and the `Cards` table and its `sync-cards` edge function are dormant for the same reason. Don't reach for Supabase when changing anything about card data. `getActualExpansion`/`getActualColor` in `cardsResponseMapper.ts` run at **map time, not render time** — after changing them, force a **Resync data** (or clear `codex_cards_v3`) or you are looking at cards mapped by the old code.
- **Card and talent artwork is resolved through the module-scope `Map`s in `@/shared/hooks/useCardImageSrc`**, never a per-render linear `.find` over the ~3100-entry `card-artwork.json` — Cardex resolves artwork once per rendered row. Cardex uses the hook; Skilldex uses the plain `getCardImageSrc` from the same module, because its nodes are drawn by D3 outside React's render. Both come from `card-artwork.json` (Blightbane treats talents as cards, art in the same `/images/icons/` namespace), so don't add a talent-specific data file or an artwork field to the Talents table. The same rule covers the event data: `EVENTS_BY_NAME` in `src/booty/utils/treasureHelper.ts` is the one map over `event-trees.json` for Booty (read artwork off it via `getEventArtwork`), and `getCardsByName` there caches the name→card lookup on the card array's identity so a modal doesn't rebuild a ~3000-entry map per render.
- **The same name can carry different artwork per `category`, so pass the category when resolving.** 34 names have multiple entries, 33 with two or more non-null artworks — e.g. `"Bulwark"` is `abilityart_1_59` as a card but `cardart_5_23` as a talent. `getCardImageSrc(name, fallback?, category?)` looks up `name|category` first, then falls back to name-only, then to the fallback image. Cardex passes `card.category`; Skilldex passes the exported `TALENT_ARTWORK_CATEGORY` (**10** — 386 entries, matching the ~385 known talents). The name-only fallback is load-bearing: 19 of those 33 names have no category-10 entry, so a category-only lookup would leave those talents blank. Null artworks are filtered out before either map is built, so they can never shadow a populated sibling. Verified when introduced: all 386 category-10 entries resolve to their own artwork, and 3 cards were _fixed_ (`Blessed`, `Runic Repel`, `Siphon Sanity`) with no regressions.
- **A dozen card names still collide on name _and_ category with different artwork** (low/high-tide and normal/`_infernal` variants — distinct cards sharing a name), so first-entry-wins picks one arbitrarily. Since Cardex shows both twins, this is visible there: both rows show the same art. `src/specs/card-metadata.md`'s id-keyed file is the fix. Nothing in `card-artwork.json` separates them; fixing it needs a new discriminator from the Blightbane source data via `scripts/fetch-card-artwork-mapping.js`, not a smarter lookup. Don't add retry or heuristic matching in the hook. Lookups must use the JSON's key verbatim: some artwork names carry curly apostrophes, typos, and set suffixes (`"Typhon's Cunning"` → `"Thyphon’s cunning_eclypse-miniset"`), so no amount of transforming a card name produces the filename, and normalizing quotes on either side of the lookup breaks it. A missing name or `artwork: null` is the **only** reliable miss signal: blightbane.io serves a valid placeholder webp with HTTP 200 for non-existent icons, so `onError` never fires for a wrong artwork value.
- Tree layout/rendering changes are verified **visually** (before/after comparison in the dev server, incl. expanded/collapsed nodes and zoom levels), not with unit tests. The **user** runs the dev server and does the comparison — don't start one yourself (see Working Style in the root `CLAUDE.md`).
